# Problem 1 CNN Accelerator for SR

## 1. Baseline code

본 프로젝트의 베이스라인 하드웨어는 `hw/cnn_accel`에 있는 3-layer ESPCN용 CNN 가속기이다. 입력은 128×128 그레이스케일 영상이며, Ti=To=16으로 병렬 MAC을 수행하고 AHB 버스를 통해 외부 SRAM에서 영상을 DMA로 읽어 온칩 `in_img`에 저장한 뒤, 레이어 단위로 convolution–batchnorm–activation을 반복한다. 중간 특징맵은 두 개의 DPRAM 뱅크에 ping-pong으로 두고, 마지막 레이어 출력 채널(4채널)은 BMP writer로 덤프하여 소프트웨어 기준 ofmap과 비교한다.

주요 모듈 구성은 다음과 같다. 상위는 `top_system`과 `top_system_tb`이고, 가속기 본체는 `cnn_accel`이다. 제어는 `cnn_fsm`이 VSYNC/HSYNC/DATA 타이밍과 픽셀·탭 인덱스를 만들고, 연산은 `conv_kern`–`mac_kern`–`mac`과 `bnorm_quant_act`(및 bias/act shifter)가 담당한다. 가중치·scale·bias는 SPRAM에 hex로 초기화되며, 영상 이동에는 `dma2buf`와 AHB 인터커넥트가 쓰인다. 시뮬레이션 출력은 `bmp_image_writer`가 담당한다.

베이스라인 테스트벤치에서 3개 레이어의 대표 설정은 bias_shift가 9/17/17, act_shift가 7/7/7이고, 첫 레이어만 first-layer merge로 `is_conv3x3=0`, 이후 두 레이어는 3×3이다. 검증 스크립트 `check_hardware_results.m`은 `out_sw`의 L03 ofmap과 하드웨어 BMP를 채널별로 비교한다.

### (a) Configuration

2025Spring 네트워크는 8개의 convolution 단과 그 뒤의 sub-pixel(픽셀 재배열) 및 residual 합성으로 구성된다. 대략적인 레이어 역할은 다음과 같다. 1번 레이어는 입력 1채널을 16채널로 올리는 3×3이나, 하드웨어에서는 first-layer merge 때문에 `q_is_conv3x3=0`으로 두어 한 사이클에 이웃 픽셀을 묶어 처리한다. 2번과 7번은 1×1 convolution이고, 3~6번과 8번은 3×3이다. 8번 레이어만 출력 채널이 4이며 마지막 레이어 플래그와 linear activation을 사용한다. 이후 4채널을 2×2 sub-pixel로 풀어 256×256 고해상도에 가깝게 재배열하고, 저해상 입력을 업샘플한 성분과 더하는 residual 경로가 붙는다.

하드웨어에 넘기는 레이어별 제어·시프트 값은 `test_vector_2025Spring.mat`에서 읽어 테스트벤치에 넣은 것과 동일하며, 이를 Table II로 정리한다. (표는 기존 PDF의 Table II를 그대로 사용.)

**Table II 해석.** `q_is_first_layer`는 레이어 1만 1이고, `q_is_last_layer`는 레이어 8만 1이다. `q_is_conv3x3`는 레이어 1·2·7이 0, 나머지 3×3 구간이 1이다. 특히 레이어 1은 구조상 3×3이지만 merge 스케줄 때문에 플래그를 0으로 두는 점이 중요하다. `bias_shift`는 16, 22, 이후 대부분 23, 마지막만 24이고, `act_shift`는 앞쪽 레이어가 1, 7·8번이 0이다. 이 값들은 batch-norm과 양자화 시 고정소수점 정렬에 쓰이므로, 소프트웨어와 한 비트라도 어긋나면 ofmap이 크게 달라진다. `LAYER_CONFIG` 워드에는 first/last/conv3x3/act_type과 layer_index, bias_shift, act_shift가 비트 필드로 패킹된다.

### (b) Data preparation

소프트웨어 추론이 끝나면 `write_cnn_model_to_hex_file.m`으로 하드웨어용 hex를 만든다. 입력 영상은 8 bit·32 bit 형태로 저장되고, 가속기는 주로 `butterfly_32bit.hex`를 DMA로 읽는다. 가중치는 레이어 1에 `export_weight_to_file_merge`, 이후 레이어에 `export_weight_to_file_reorder`를 적용한 뒤 `all_conv_weights.hex`로 합친다. scale과 bias도 레이어별로 뽑아 `all_conv_scales.hex`, `all_conv_biases.hex`로 모은다. 이 파일들을 `hw/cnn_accel_2025Spring/input_data/`(및 필요 시 `img/`)로 복사하고, 검증용으로 마지막 레이어 ofmap BMP를 `out_sw/`에 둔다.

[그림 삽입: output_hex_file / input_data hex 목록]

버퍼 용량은 Table III와 같다. (표는 기존 PDF의 Table III 사용.) Weight는 라인당 128 bit이며 레이어별 라인 수가 16, 16, 144, 144, 144, 144, 16, 144로 합계 **768워드**이다. Scale과 Bias는 라인당 16 bit이고 레이어마다 To=16개씩 패딩되어 8×16=**128워드**이다.

Table III에 정리한 weight, scale, bias 버퍼 크기가 최적인지 검토한 결과는 다음과 같다. Scale과 Bias는 레이어마다 출력 채널 수를 To(=16)에 맞춰 패딩하여 저장하므로 레이어당 16워드가 필요하고, 8개 레이어를 합치면 총 128워드가 된다. 이는 실제 필요량과 일치하므로 Scale/Bias 버퍼는 최적에 가깝다고 볼 수 있으며, 워드당 16 bit를 기준으로 하면 각각의 총 용량은 128×16=2,048 bit이다.

이에 비해 Weight는 레이어 종류에 따라 필요한 워드 수가 달라진다. 첫 번째 레이어는 first-layer merge 방식으로, 두 번째와 일곱 번째 레이어는 1×1 convolution으로 인해 각각 16워드만 사용하는 반면, 나머지 3×3 convolution 레이어는 각각 144워드를 사용한다. 이를 모두 합하면 768워드가 되고, 워드당 128 bit를 곱하면 768×128=98,304 bit가 되어 hex 파일에 실제로 저장된 용량과 일치한다. 따라서 Table III의 weight 버퍼 크기(768워드)는 필요 하한에 해당한다.

다만 하드웨어에서 모든 레이어를 3×3으로 가정하여 N_LAYER×(Ti×To×9)/N=8×144=1152 워드로 할당하면, 실제 사용량인 768워드보다 384워드가 남는 과대 할당이 발생한다. 이러한 방식은 구현을 단순하게 만드는 장점은 있으나 메모리 효율 측면에서는 최적이 아니다.

결론적으로 Scale/Bias 버퍼는 최적에 가깝지만, Weight 버퍼는 레이어별 실제 hex 라인 수의 합인 768워드가 더 효율적이며 전 레이어를 3×3으로 통일한 1152워드 할당은 suboptimal하다. 즉 Table III의 값 자체는 타당하지만, 하드웨어에서 최대 크기만으로 단순 할당하는 설계는 최적 설계라고 보기 어렵다.

## 4. H/W simulation and verification for 2025Spring

2025Spring 하드웨어는 `hw/cnn_accel_2025Spring`에서 `N_LAYER=8`로 두고, Table II의 시프트·플래그를 레이어 루프마다 기록한 뒤 DMA로 영상을 적재하고 여덟 레이어를 순차 실행한다. 가중치 베이스 주소는 1×1이면 To워드, 3×3이면 To×9워드씩 진행하고, scale/bias 베이스는 레이어마다 To씩 진행한다. 클록은 100 MHz(주기 10 ns), 해상도는 128×128이다.

# Problem 2: Optimization

*(상세 본문은 아래와 동일 내용이며, 별도 파일 `cnn_accel_opt/보고서_Problem2_본문.md`와 같습니다.)*

## 1. Optimization

### (a) Problem and scopes

베이스라인 CNN 가속기(`cnn_accel`)는 128×128 입력에 대해 3개 레이어 ESPCN을 Ti=To=16, 동작 주파수 100 MHz로 수행한다. 과제에서 제시한 베이스라인 성능은 실행 시간 t0=3930 µs, 온칩 버퍼 s0=4280 Kbits이며, 전체 개선도는 S_overall=(t0/t)×(s0/s)로 평가한다. 여기서 클록 주파수, Ti/To, 입출력 해상도는 변경할 수 없으므로, 개선은 데이터 이동·제어 공백·버퍼 구조를 바꾸는 쪽으로만 가능하다.

베이스라인의 버퍼 구성을 분해하면 대략 입력 영상 버퍼 128 Kbits, 피처맵 더블 버퍼 2048×2=4096 Kbits, 가중치·bias/scale 약 55 Kbits 수준으로, s0의 대부분이 피처맵 두 장에 묶여 있다. 시간 측면에서는 라인마다 긴 HSYNC 공백(약 160 사이클)과, 레이어 3에서 Cout=4인데 To=16인 점 때문에 커널 유휴 비율이 큰 것이 병목으로 알려져 있다. 본 최적화는 `hw/cnn_accel_opt`에서 위 제약을 지키면서 실행 시간과 버퍼를 동시에 줄이는 것을 범위로 한다.

[그림 삽입: 베이스라인 버퍼/데이터패스 구조도]

### (b) Optimization methods

강의에서 제시된 방향은 (1) 입력 재배치와 DMA 트랜잭션 수 감소, (2) DMA와 convolution 파이프라이닝으로 입력 버퍼 축소, (3) Layer 3에서 convolution 커널 완전 활용, (4) layer fusion이다. 본 설계는 기능 동등성(`check_hardware_results.m` 일치)을 깨지 않는 선에서 효과가 큰 항목을 우선 적용하였고, 아래는 실제 수정한 코드이다. 주요 변경 파일은 `cnn_accel.v`, `cnn_fsm.v`, `top_system.v`, `top_system_tb.v`이다.

**첫째, 입력 DMA 패킹(4픽셀/워드).** AHB 32 bit에 맞게 `butterfly_32bit_reorder.hex`를 쓰고, 라인당 전송 횟수를 WIDTH/4로, 주소 증가를 WIDTH 바이트로 두었다. valid마다 `in_img`에 네 바이트를 쓴다.

테스트벤치에서 패킹 hex와 워드 수:

```verilog
// top_system_tb.v
parameter N_WORD = WIDTH * HEIGHT / 4;
parameter INIT_FILE = "img/butterfly_32bit_reorder.hex";
parameter N_CELL = 304;   // weight words: 16+144+144
```

DMA 전송 횟수·라인 stride (`cnn_accel.v`):

```verilog
parameter PIX_PER_WORD = 4;
// ...
num_trans_ld = q_width / PIX_PER_WORD;   // 128 -> 32 beats/line
// ...
start_addr_ld <= start_addr_ld + q_width; // byte stride (not WIDTH*4)
```

픽셀 언팩 저장:

```verilog
if(data_vld_o_ld) begin
    in_img[in_pixel_count + 0] <= data_o_ld[ 7: 0];
    in_img[in_pixel_count + 1] <= data_o_ld[15: 8];
    in_img[in_pixel_count + 2] <= data_o_ld[23:16];
    in_img[in_pixel_count + 3] <= data_o_ld[31:24];
end
```

[그림 삽입: reorder hex / Vivado INIT 설정 캡처(선택)]

**둘째, HSYNC 축소와 라인버퍼 prefetch.** DATA 중에 다음 하단 행을 `lb_next`로 읽어 두고, HSYNC에서는 윈도우만 한 줄 밀어 올려 HSYNC_DELAY=2로 두었다.

```verilog
// top_system_tb.v — 레이어마다 delay 기록
q_start_up_delay = q_is_first_layer ? 12'd160 : 12'd420;
q_hsync_delay    = 12'd2;
task_AHBwrite(`CNN_ACCEL_DELAY_PARAMS, {q_hsync_delay, q_start_up_delay});
```

fmap 읽기: VSYNC 때 초기 2줄 적재, DATA 때 row+2 prefetch.

```verilog
// cnn_accel.v
wire lb_load_issue = ... && (lb_load_cnt < LB_PRELOAD_WORDS); // 2*WIDTH
wire lb_pref_issue = ... && ctrl_data_run
    && (lb_pref_cnt < q_width) && ((row + 2) < q_height);
// ...
fmap_buf_addrb = (row + 2) * q_width + lb_pref_cnt; // prefetch
```

HSYNC에서 시프트·설치:

```verilog
if(!q_is_first_layer && ctrl_hsync_run && (ctrl_hsync_cnt == 0)) begin
    lb_pref_cnt <= 0;
    if(row >= 1) begin
        for(gi=0; gi<2*WIDTH; gi=gi+1)
            sw_linebuf[gi] <= sw_linebuf[gi+WIDTH];
        for(gi=0; gi<WIDTH; gi=gi+1)
            sw_linebuf[2*WIDTH+gi] <=
                ((row+1) < q_height) ? lb_next[gi] : {To*ACT_BITS{1'b0}};
    end
end
```

**셋째, 단일 fmap + 3줄 라인버퍼(부분 layer fusion).** 두 번째 DPRAM을 삭제하고 `u_fmap_buff` 하나만 남겼다. L2/L3 din은 `sw_linebuf`에서 읽는다.

```verilog
localparam LINE_BUF_WORDS   = 3 * WIDTH;  // n = 3
localparam LB_PRELOAD_WORDS = 2 * WIDTH;  // row0: [0, fmap0, fmap1]
reg [To*ACT_BITS-1:0] sw_linebuf [0:LINE_BUF_WORDS-1];
reg [To*ACT_BITS-1:0] lb_next    [0:WIDTH-1];

wire fmap_wr_en = vld_o[0] && !q_is_last_layer;
dpram #(.W_DATA(To*ACT_BITS), .N_WORD(FRAME_SIZE))
u_fmap_buff( /* 단일 뱅크 */ );
```

라인버퍼에서 3×3 탭을 읽는 경로(L2/L3 공통):

```verilog
// boundary pad + sw_linebuf[tap_r*WIDTH + col]
boundary = (is_first_row && (tap_r==0)) || (is_last_row && (tap_r==2))
        || (tap_c < 0) || (tap_c >= q_width);
lb_idx   = tap_r*WIDTH + clamp(tap_c);
din_tap0 = boundary ? 0 : sw_linebuf[lb_idx];
```

**넷째, Layer 3 multipixel.** 픽셀 4×OC 4 매핑은 마지막 행 끝 픽셀 불일치로 최종본에서 끄고 stride=1을 유지했다(`cnn_fsm.v`의 `col_stride = 1`). 시간 이득은 DMA·HSYNC에, 버퍼 이득은 fmap 단일화에 두었다.

**다섯째, 가중치 SPRAM 적정화.**

```verilog
// cnn_accel.v — was 3*144=432
parameter N_CELL = 304;  // 16 + 144 + 144
```

이상으로 수정 코드의 핵심은 (i) DMA 패킹·stride, (ii) HSYNC=2 + prefetch/shift, (iii) fmap 1뱅크+`sw_linebuf`/`lb_next`, (iv) `N_CELL=304`이다.
### (c) Evaluation

기능 검증으로, Vivado에서 `top_system_tb`를 시뮬한 뒤 `out/convout_ch01`~`04.bmp`를 얻고 `check_hardware_results.m`으로 `out_sw`의 L03 ofmap과 비교한다. 네 채널 모두 `max_diff==0`이어야 베이스라인과 동일하게 동작한다고 본다.

[그림 삽입: MATLAB same! 출력]

이어서 과제에서 요구한 실행 시간 t와 버퍼 크기 s, 그리고 전체 개선도 지표를 보고한다. 전체 개선도는 다음 식으로 정의된다.

S_overall = (t0 / t) × (s0 / s)

여기서 t0, s0는 각각 베이스라인의 실행 시간과 버퍼 크기이고, t, s는 최적화 설계의 값이다. 과제에서 제시한 베이스라인 값은 t0 = 3930 µs, s0 = 4280 Kbits이다.

본 설계의 온칩 버퍼 s는 선언된 저장 요소의 합으로 계산한다. in_img 128 Kbits, fmap 단일 뱅크 2048 Kbits, 3줄 라인버퍼(sw_linebuf) 48 Kbits, prefetch 줄(lb_next) 16 Kbits, weight 약 39 Kbits, bias/scale 약 1.5 Kbits를 더하면

s = 128 + 2048 + 48 + 16 + 39 + 1.5 = 2280.5 Kbits

이므로 버퍼 쪽 이득은 s0/s = 4280/2280.5 ≈ 1.877이다.

실행 시간 t는 테스트벤치 출력으로 측정하였다. 시뮬레이션 종료 시 `OPT DONE: t = 3194 us`(sim time 3193965000)가 관측되었으므로 t = 3194 µs이다. 이를 대입하면

S_overall = (3930/3194) × (4280/2280.5) ≈ 1.230 × 1.877 ≈ 2.309

이다. 즉 시간 측면에서 약 1.23배, 버퍼 측면에서 약 1.88배 개선되어, 전체 지표는 약 2.31이다.

## 2. Optimality analysis

라인 윈도우 n=3을 고른 이유는 3×3이 한 출력 행에 입력 세 줄을 필요로 하기 때문이다. n<3이면 할로가 부족하고 n>3이면 SRAM만 는다. 두 번째 전체 fmap 대비 수십 Kbits로 같은 역할을 하므로 s0/s에 가장 직접적이다.

첫 행은 [패드, row0, row1]이어야 하므로 초기 적재는 2×WIDTH만 읽고 상단을 0으로 둔다. [row0,1,2]로 채우면 중심이 밀려 상단 행이 깨진다. START_UP=420은 가중치(최대 144)와 이 적재(256)를 덮는다.

HSYNC=2는 DATA 중 prefetch와 짝을 이룬다. prefetch 없이 HSYNC에서 128워드를 읽으면 공백이 다시 커진다. DMA 패킹 인수 4는 32 bit 버스와 8 bit 픽셀의 비이다. N_CELL=304는 weight hex의 필요 하한이다.

L3 multipixel은 이론상 L3를 약 4배 빠르게 하나 마지막 픽셀 묶음에서 기준과 어긋나, 검증 전제를 지키려 보류했다. 입력 버퍼를 n줄만 남기는 DMA–L1 파이프라인은 줄일 양이 128 Kbits뿐이라 fmap 뱅크 제거보다 우선순위가 낮다.

정리하면 핵심 파라미터는 n=3(+prefetch 1줄), HSYNC=2, DMA×4, N_CELL=304이며, 실측 기준으로 버퍼 s=2280.5 Kbits, 실행 시간 t=3194 µs, S_overall≈2.309를 얻었다.
